## Verifikasi dan retry

Proses membaca manifes percobaan asli, memeriksa ID file rescue terpisah, ukuran serta SHA-256 metadata Drive, lalu memverifikasi SHA-256 unduhan. TAR diekstrak ke ruang sementara dengan validasi path dan tipe anggota. Verifikator asli memeriksa identitas lengkap yang disimpan, versi checkpoint, induk `None`, inventaris dan hash isi setiap file, tanpa membuka pickle sebagai objek. Jika checkpoint lokal sudah ada, segelnya harus cocok. Pada runtime baru, hasil ekstraksi yang lulus disegel di workspace, sehingga dapat langsung digunakan untuk RESUME di runtime tersebut.

Runner mengunggah byte TAR yang sama ke slot Drive yang telah dipesan dengan nama sementara dan metadata segel. Runner membaca ulang ukuran dan SHA-256 server sebelum mengganti nama menjadi `checkpoint-operations.tar`, lalu memverifikasi slot resmi lagi. Uploader memakai HTTPS resumable dengan redirect otomatis dimatikan. Respons HTTP 308 memberi posisi byte lewat `Range`. Setelah gangguan jaringan, uploader menanyakan posisi sesi. Jika respons akhir hilang, hanya metadata Drive yang cocok yang dapat mengonfirmasi unggahan.

- Pada runtime baru, sediakan ruang lokal sekitar dua kali ukuran TAR ditambah 2 GiB untuk unduhan dan ekstraksi. Drive memerlukan ruang tambahan untuk salinan resmi karena file rescue independen tetap disimpan. Jangka waktu transfer bergantung pada koneksi dan kuota.
- Jika transfer atau publikasi gagal, jalankan **Registrasi Rescue Operations** lagi dengan nilai yang sama. Arsip sementara yang cocok dapat dipublikasikan kembali tanpa unggah ulang. File resmi dengan checksum berbeda menyebabkan proses berhenti. Jika ada error saat verifikasi, tahan RESUME dan periksa Monitor Drive.
- Registrasi dapat memverifikasi arsip pada runtime baru tanpa menjalankan kode simulasi. RESUME masih memeriksa kecocokan runtime dengan manifes asli, termasuk versi Python, NumPy, PyArrow dan data zona waktu. Gunakan profil runtime semula bila perbandingan gagal.
